# Albugent v2.0 — Autonomous Data Governance Agent

Albugent is an autonomous AI agent that audits SQLite datasets for data quality issues and PII, reasons over the findings using its own judgment, and ships the results as a ready-to-review GitHub Pull Request — plus a live web dashboard for human-in-the-loop review and one-click remediation.

Built with the [Strands Agents SDK](https://strandsagents.com) on AWS Bedrock.

---

## The Problem

Data catalogs (e.g. DataHub) excel at **detection** — surfacing schema, lineage, and quality signals. But closing the gap between detection and safe, reviewed remediation still falls to a human: someone still has to write the fix, get it reviewed, and ship it. Albugent automates that gap without removing the human from the loop — every fix is generated by a deterministic engine, never by the LLM directly, and nothing is written back to production data until a person explicitly approves it.

It's built for teams without the resources to run a full catalog deployment, and for teams that already run one but need a safe automation layer on top.

---

## What's New in v2.0

The original CLI-only agent (scan → SQL → PR) is still fully intact and working. v2.0 adds a full web layer on top:

- **FastAPI backend** (`web_api/main.py`) exposing dashboard data and remediation actions over HTTP
- **React + Vite + Tailwind frontend** (`web-ui/`) — a live governance dashboard with:
  - KPI banner (data assets, tables scanned, PII columns, policy violations)
  - Per-domain downstream lineage map
  - Pending Proposals queue with one-click **Approve** / **Reject**
  - Data Quality Insights and PII Distribution (severity-classified)
  - Live Metrics chart tracking KPI movement over the session
  - "Generate PR" button that triggers the original agentic Phase 2 flow from the browser
- **Independent remediation patches** — anomalies are no longer bundled into one SQL blob per table; each is a separately identified, separately applicable `RemediationPatch`
- **Write-path isolation** — the function that actually applies a patch (`patch_applier.py`) is a plain Python function, *not* an MCP tool. The LLM/agent has no access to it under any circumstance; only an explicit human action (an API call triggered by clicking Approve) can invoke it
- **`check_row_impact` tool** — generic cross-table impact analysis using existing lineage discovery, with an explicit `join_confidence` flag (`exact_key_match` vs `pii_name_match`) so the UI can show when a lineage join relies on a non-unique key like a name

## How It Works

Albugent has two independent entry points into the same underlying logic:

### Entry point A — CLI agent (`agent.py`), full agentic PR flow

**Phase 1 — Deterministic Context & SQL Generation (no LLM)**
1. `scan_enterprise_datasets()` scans `data/<domain>/*.db` and builds a registry of every table, keyed by a DataHub-style URN.
2. Pure-Python profilers run: null-rate analysis, numeric range checks, date-logic inversion checks (role-aware — see below), PII column detection, and lineage-aware risk scoring.
3. `generate_remediation_sql()` turns every detected anomaly into a safe, deterministic SQL fix — one `DROP TABLE IF EXISTS` / `CREATE TABLE cleaned_<table>` pair per dataset.

This half never touches an LLM. The SQL in the PR is 100% reproducible from the data.

**Phase 2 — Agentic Investigation & Report (Strands + Bedrock)**
1. A Strands `Agent`, backed by Amazon Bedrock (Nova Pro), connects to the MCP server over stdio with a limited, read-only toolset.
2. The agent decides for itself how to investigate each dataset — order and reasoning are its own, not scripted.
3. The agent composes a consolidated governance report (Table of Quality Variances, PII Detections, Circuit Breaker Status), built deterministically in Python from tool outputs — **not** generated by the LLM. The only LLM call in this phase writes a 3–4 sentence executive summary, with no tool access and no ability to introduce facts not already given to it in the prompt.
4. The agent never writes remediation SQL itself.

**Phase 3 — PR Delivery**
The SQL artifact and the report are combined into a Draft PR via the GitHub API.

### Entry point B — Web dashboard (`web_api/` + `web-ui/`), human-in-the-loop review

1. FastAPI imports the same `mcp_server/utils/*` functions directly as Python — no LLM involved in this path at all.
2. `/api/proposals` calls `generate_remediation_patches()` per dataset, returning one `RemediationPatch` per detected anomaly (not a bundled SQL script).
3. A person reviews each patch in the browser and clicks **Approve** or **Reject**.
4. Approve calls `patch_applier.apply_patch()` directly — a plain Python function, never exposed as an MCP tool — which runs the corresponding `UPDATE` against the live SQLite file.
5. The **Generate PR** button in the dashboard triggers the same Phase 1 + Phase 2 flow as the CLI agent, via `/api/generate-pr`.

Both entry points read and write the same `.db` files in `data/`. Anomalies fixed through the dashboard will no longer appear next time the CLI agent runs, and vice versa.

## Setup

### Prerequisites

- Python 3.11+, Node.js 18+
- An AWS account with Bedrock model access (Nova Pro or your chosen model)
- A GitHub Personal Access Token with `repo` scope (for PR creation)

### Environment Variables

Create a `.env` file in the project root:

```bash
AWS_ACCESS_KEY_ID=your_access_key
AWS_SECRET_ACCESS_KEY=your_secret_key
AWS_REGION=us-east-1
AWS_BEDROCK_MODEL_ID=amazon.nova-pro-v1:0
GH_TOKEN=your_github_personal_access_token
GITHUB_REPOSITORY=your-username/your-repo
```

### 1. Backend (FastAPI + MCP server)

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
python -m pip install --upgrade pip
pip install -r agent/requirements.txt
pip install fastapi uvicorn

uvicorn web_api.main:app --port 8000
```

This starts the dashboard API on `http://localhost:8000` and scans all datasets under `data/` on startup.

### 2. Frontend (React dashboard)

In a separate terminal:

```bash
cd web-ui
npm install
npm run dev
```

Open the printed local URL (typically `http://localhost:5173`). The dashboard fetches from `http://localhost:8000` — keep the backend running.

### 3. CLI agent (optional — full agentic PR flow)

Runs independently of the web stack:

```bash
python agent/agent.py
```

This scans all datasets, generates the deterministic SQL artifact, runs the Strands agent's investigation, and opens (or updates) a Draft PR. The same flow is also triggerable from the dashboard via the **Generate PR** button, which calls `/api/generate-pr`.

## API Reference (`web_api/main.py`)

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/kpi-summary` | GET | Data assets, tables scanned, PII column count, policy violations |
| `/api/proposals` | GET | All pending remediation patches across every dataset |
| `/api/proposals/{patch_id}/approve` | POST | Applies the patch directly to the SQLite file (write-only, no LLM) |
| `/api/proposals/{patch_id}/reject` | POST | Dismisses the patch from the queue (no data change) |
| `/api/pii-distribution` | GET | PII columns bucketed by severity (High/Medium/Low) |
| `/api/quality-insights` | GET | Top anomalies ranked by affected-row percentage, plus an overall score |
| `/api/lineage-graph` | GET | Nodes (datasets) and edges (lineage) for the dashboard's lineage map |
| `/api/generate-pr` | POST | Triggers the full CLI agent flow (Phase 1 + Phase 2), returns `{status, pr_url}` |

## MCP Tools

Exposed by `mcp_server.py`. Callable by the Strands agent over stdio, and also importable directly as Python (used by `web_api/main.py`):

| Tool | Purpose |
|---|---|
| `list_available_datasets` | Returns all registered dataset URNs |
| `inspect_dataset_schema` | Columns, tags, and detected PII fields for a dataset |
| `auto_profile_dataset_anomalies` | Full anomaly profile + downstream lineage impact |
| `score_dataset_risk` | Combined PII + freshness + centrality risk score |
| `score_all_datasets_risk` | Aggregated risk across the whole registry |
| `check_row_impact` | Generic cross-table impact analysis via lineage + schema intersection, flags `join_confidence` |
| `get_circuit_breaker_status` | HALTED / MONITOR / OK status per dataset, with triggering anomaly |
| `get_remediation_patches` | Independent, per-anomaly remediation patches for a dataset |
| `execute_sql_query` | Read-only (`SELECT`/`PRAGMA` only) ad-hoc querying |
| `calculate_pipeline_centrality` | Betweenness centrality across the lineage graph |
| `get_dataset_sample` | Sample rows for manual inspection |

**Write operations are never exposed as MCP tools.** `patch_applier.apply_patch()` is a plain Python function called only from `web_api/main.py`'s approve endpoint, in direct response to an explicit human action. The agent has no code path to it.

## Anomaly Detection Approach

- **Numeric anomalies**: negative-value checks, with an explicit exclusion for columns where negative values are legitimate (e.g. geographic longitude)
- **Date-logic anomalies**: role-aware pairing — a column must match a `START_KEYWORDS` term (`admission`, `pickup`, `shipped`, ...) or an `END_KEYWORDS` term (`discharge`, `dropoff`, `delivered`, ...) to be paired at all. This prevents false pairings between unrelated date-like columns (e.g. an aggregate date column incorrectly paired against an unrelated timestamp)
- **NULL-rate classification**: a 20% threshold distinguishes likely data-entry errors from nullable-by-design fields (e.g. a shipment's delivery date while still in transit). Columns above this threshold are excluded from `null_fill` remediation entirely — they are surfaced as informational, not auto-fixed
- **PII detection**: keyword-based column matching, with a severity classification (`High`/`Medium`/`Low`) layered on top for the dashboard's PII Distribution view

## Known Limitations

- **Circuit breaker logic is partially implemented.** Lineage-aware halt propagation exists (`circuit_breaker.py`), but it is not yet wired into an automated control system that gates downstream processing.
- **No automated test suite yet.** Correctness has been verified by manual execution, not CI-gated tests.
- **PII detection is keyword-based, not NLP/ML-based.** It will miss PII in columns with non-obvious names and may over-flag columns with matching substrings.
- **No dataset-registry caching.** Every API call re-profiles data directly from disk; fine for the demo dataset sizes, not optimized for large-scale production data volumes.
- **Live Metrics chart resets on page reload** — it tracks changes only within the current browser session, not historical data.
